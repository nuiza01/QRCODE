# NQR-129 v2 — ขอบเขต release gate หลังบังคับล็อกอิน (PM-owned)

วันที่ 2026-09-18 (Asia/Bangkok) | ผู้เขียน: Claude (PM) | ผู้ตัดสินทิศทาง: Product Owner

เอกสารนี้**แทนที่ §1 และ §7** ของ [PHASE2A_RELEASE_GATE_CHANGE_SPEC.md](handoff-evidence/2026-09-16/PHASE2A_RELEASE_GATE_CHANGE_SPEC.md) `4243bacdddf6794f08ced2fb0befa290af2c65ea05167593e504540e4b9ef34d` ส่วนอื่นของ spec เดิม (§2–§6, §8) ยังใช้ได้และห้ามแก้ไฟล์เดิม เพราะเป็นหลักฐานที่ถูก freeze ไว้

## 1. ทำไมต้องมี v2

2026-09-18 Product Owner ตัดสินว่าใช้ตัวสร้าง QR ได้เฉพาะคนที่ล็อกอิน generator จึงย้ายจากหน้า public ที่ prerender ไปอยู่ที่ `/[locale]/create` ซึ่งเป็น route แบบ dynamic ที่ตรวจ session ฝั่งเซิร์ฟเวอร์

ผลที่วัดได้จาก artifact จริง (ดู [PM_PHASE2A_GATE_SCOPE_AFTER_LOGIN.md](reports/PM_PHASE2A_GATE_SCOPE_AFTER_LOGIN.md)): HTML ที่ prerender ของหน้า public ไม่อ้างถึง chunk ที่มี marker ต้องห้ามเลย เกณฑ์เดิมจึงผ่านเพราะ "ไม่มีอะไรให้ตรวจ" ไม่ใช่เพราะการโหลดถูกควบคุม gate ที่ไม่ได้ตรวจสิ่งที่ต้องป้องกันคือ gate ที่ให้ความมั่นใจผิด ๆ

## 2. ขอบเขตใหม่: สองพื้นผิว ไม่ใช่พื้นผิวเดียว

### 2.1 พื้นผิว A — หน้า public ที่ prerender (22 route เดิม)

- **สิ่งที่ต้องพิสูจน์:** ไม่มี marker ต้องห้าม (`qr-code-styling`, `updateVendorMatrix`, `getModuleCount`, `svg2pdf`, `jsPDF`) ใน chunk ที่เข้าถึงได้ตอน startup ของทุก route และไม่มี chunk ของ generator ถูกดึงเข้ามาโดยอ้อม
- **วิธีตรวจ:** เหมือนเดิมทุกประการ (adapter อ่าน HTML + static chunk) ซึ่ง iteration 8 ที่ integrate แล้วทำได้อยู่
- **เหตุผลที่ยังต้องมี:** วันนี้ผ่านเพราะ generator ย้ายออก ถ้าวันหน้ามีใครใส่ preview กลับเข้าหน้า public เกณฑ์นี้จะจับได้ทันที

### 2.2 พื้นผิว B — `/[locale]/create` (dynamic, ต้องล็อกอิน)

- **สิ่งที่ต้องพิสูจน์:** เกณฑ์เดิมของ NQR129 ทั้งหมด แต่ย้ายที่วัด
  - chunk เริ่มต้นของ route นี้ต้องไม่มีโค้ดเฉพาะ PDF
  - renderer/QR vendor โหลดได้เมื่อมี preview ที่ valid ปัจจุบัน mount โดยไม่ต้องคลิก
  - PDF โหลดเมื่อมีคำขอ PDF ที่ผ่านเงื่อนไขเท่านั้น
- **วิธีตรวจแบบ static โดยไม่ต้องเปิดเซิร์ฟเวอร์:** build เขียน `.next/server/app/[locale]/create/page_client-reference-manifest.js` และ `.next/build-manifest.json` ซึ่งระบุชุด chunk ฝั่ง client ของ route นี้ adapter อ่านสองไฟล์นี้แล้วประกอบเป็น "ชุด chunk เริ่มต้นของ route" ได้ ถ้ารูปแบบไฟล์ไม่ตรงกับที่ review ไว้ ต้องตอบ UNKNOWN ตามเดิม ห้ามเดา
- **ข้อจำกัดที่ต้องเขียนไว้ตรง ๆ:** route นี้ไม่มี HTML ที่ prerender ให้ตรวจ การพิสูจน์จึงอาศัย manifest ของ build ไม่ใช่ HTML ที่ผู้ใช้จะได้รับจริง ส่วนที่เหลือต้องมาจากหลักฐาน browser ใน §3

## 2.3 สิ่งที่การตรวจแบบ static อ้าง และไม่อ้าง (แก้ 2026-09-18 โดย Product Owner)

เดิม Stage A ตั้งเกณฑ์ว่า **ทุก statement ในทุกโมดูลต้องอยู่ในรูปแบบที่ review แล้ว** เมื่อวัดกับ artifact จริงพบว่าเกณฑ์นี้ให้ UNKNOWN 516 รายการเฉพาะในชุด startup เพราะเนื้อของ factory คือโค้ดของโมดูลเอง (React, โค้ดแอป, ไลบรารี) การทำตามเกณฑ์นี้จึงเท่ากับการ review ภาษา JavaScript ทั้งภาษา Product Owner ตัดสินให้**ถอนข้ออ้างนี้**

**สิ่งที่ยังอ้างได้และตรวจได้**

1. identity ของ artifact ตรงกับที่ประกาศไว้ทุกไบต์
2. construct ที่ดึงไบต์ได้ทุกตัวในโค้ด — `context.l`, `context.L`, `context.b`, `context.w`, `context.u` และ `import()` — ถูกอ่าน แปลงเป็น path และต้องชี้ไปยัง chunk ที่ artifact มีจริง ถ้าเป้าหมายไม่ใช่ literal ที่อ่านได้ ผลเป็น UNKNOWN
3. โมดูลที่ถูกอ้างถึงผ่าน context (`r`, `i`, `A`, `f`, `s`) ต้องมีการลงทะเบียนอยู่ใน artifact
4. path ของ chunk ที่ปรากฏนอก construct ที่รู้จัก ถูกตั้งธงเป็น UNKNOWN
5. chunk ในชุด startup ต้องไม่มี marker ของ PDF/renderer

**สิ่งที่ไม่อ้างอีกต่อไป**

- ความหมายของโค้ดในเนื้อโมดูล
- ลำดับเวลาของการโหลด — ข้อนี้มาจากหลักฐานเบราว์เซอร์ใน §3 เท่านั้น

ผลที่ตามมาสำหรับผู้ตรวจ: การอ่านรายงานของ gate ต้องไม่ตีความว่า PASS แปลว่า "โค้ดทุกบรรทัดถูกตรวจแล้ว" แต่แปลว่า "ไม่มีเส้นทางการดึงไบต์ที่ตามไม่ได้ และไม่มีโค้ด PDF/renderer ในชุดเริ่มต้น"

## 3. โปรโตคอลหลักฐาน browser (แทน §7 เดิม)

เงื่อนไขก่อนเริ่ม: เครื่องมือ browser ที่อนุมัติแล้วใช้งานได้จริง, artifact ที่ freeze แล้ว, และ **บัญชีทดสอบสำหรับล็อกอิน** ซึ่งเป็นของใหม่ที่ spec เดิมไม่มี หลักฐานต้องระบุว่าใช้บัญชีใด session ถูกสร้างเมื่อใด และหมดอายุเมื่อใด ห้ามใช้บัญชีจริงของผู้ใช้

ฉากทั้งหมดเก็บที่ `/[locale]/create` ทั้ง th และ en ครอบทุกชนิดข้อมูล 10 แบบผ่าน `?type=<slug>` ยกเว้นฉาก A1 ที่เก็บบนหน้า public

| รหัส | ฉาก | สิ่งที่ต้องบันทึก |
| --- | --- | --- |
| A1 | หน้า public ทั้ง 22 route ตอนเปิดใหม่ | ไม่มีคำขอหรือการ evaluate ของ renderer/QR/PDF ตลอดช่วงสังเกตที่ประกาศไว้ |
| B1 | เปิด `/create` ครั้งแรกด้วย session ที่ใช้งานได้ ฟอร์มว่าง | ฟอร์ม mount, ไม่มี preview ที่ valid, ไม่มีคำขอ renderer/PDF |
| B2 | เปิด `/create?type=<slug>` ครั้งแรก | ยืนยันว่า `?type=` เลือกแท็บเท่านั้น ไม่ได้เติมค่าจนกลายเป็น preview ที่ valid — ถ้าวันหน้าเปลี่ยน ฉากนี้คือที่ที่จะจับได้ |
| B3 | ว่าง → valid | บันทึก revision ของอินพุต, การ mount preview และตัวเริ่มคำขอ renderer |
| B4 | การกระทำที่ไม่ใช่ PDF (Test Scan, PNG, SVG, เปลี่ยนขนาด/สไตล์) | ไม่มีคำขอหรือการ evaluate ของโค้ดเฉพาะ PDF |
| B5 | คำขอ PDF ครั้งแรกที่ผ่านเงื่อนไข | เหตุการณ์ต้องมาก่อนการ fetch/evaluate โมดูล PDF และตรวจ helper ที่ถูก import ตามมา |
| B6 | ทำซ้ำแบบ warm และการนำทางภายใน | ระบุ cache/โมดูลที่ยังอยู่ในหน่วยความจำ การไม่มี network transfer อย่างเดียวไม่พิสูจน์ว่าไม่มีการ evaluate |

ฉาก `COLD_VALID_INITIAL_PREVIEW` เดิมถูกยกเลิก และแทนที่ด้วย B1/B2 ซึ่งเป็นคำถามเดียวกันแต่ถามในที่ที่ generator อยู่จริง จึงไม่ต้องมีกลไกยกเว้นใด ๆ ในตัว gate อีก (สาย iteration 9/10 ถูกทิ้งด้วยเหตุนี้)

เพิ่มเติมที่ spec เดิมไม่มีและต้องมี

- **B7 — หมด session ระหว่างใช้งาน:** ลบ session ในฐานระหว่างเปิด `/create` ค้างไว้ แล้วโหลดหน้าใหม่ ต้องกลับไปสถานะ "ต้องเข้าสู่ระบบ" และต้องไม่มีการโหลด renderer/PDF เพิ่ม
- **B8 — ผู้ใช้ที่ไม่ได้ล็อกอิน:** ขอ `/create` โดยไม่มี session ต้องไม่ได้รับ markup ของฟอร์มเลย (ตรวจที่ไบต์ของ response ไม่ใช่ที่หน้าจอ)

## 4. สิ่งที่ยังไม่เปลี่ยน

- §2–§6 ของ spec เดิม: identity/baseline, ความเป็นเจ้าของไฟล์ห้าไฟล์, สัญญา API, ไวยากรณ์ emission ที่รองรับ และการควบคุมการตรวจสอบ
- §8: ผู้เขียน spec ห้ามอนุมัติงานของตัวเอง ต้องมี TL และ SECURITY อิสระ
- เงื่อนไข C1/C2 ใน [runbook](RELEASE_GATE_RUNBOOK.md) และข้อจำกัดที่บันทึกไว้ทั้งหมด

## 5. ของค้างที่ต้องปิดก่อน gate จะผ่านได้จริง

1. `SUPPORTED_PROFILE.sourceInventorySha256` ยังเป็นค่าก่อน integrate release gate และตอนนี้ยังไม่รวมการเปลี่ยนแปลงของระบบล็อกอินด้วย ต้องอัปเดตพร้อมรอบ build ที่จะใช้เป็นหลักฐานจริง
2. adapter ยังจัด runtime chunk `turbopack-*` เป็น UNKNOWN ตอนนี้มี [runtime model](reports/PM_PHASE2A_TURBOPACK_RUNTIME_MODEL_SOURCE.md) และมี artifact ของเราเองเป็น fixture แล้ว จึงทำได้โดยไม่ต้องขอสิทธิ์เพิ่ม
3. ต้องเพิ่มความสามารถอ่าน manifest ของ route แบบ dynamic ตาม §2.2
4. ยังไม่มีบัญชีทดสอบสำหรับเก็บหลักฐาน browser

## 6. สิ่งที่เอกสารนี้ไม่ได้อนุญาต

ไม่อนุญาต deploy, ไม่อนุญาตแตะ production/Plesk/DNS/OAuth จริง, ไม่อนุญาตข้าม gate หรือข้ามการปฏิเสธด้านความปลอดภัย และไม่อนุญาตให้ใครอนุมัติงานของตัวเอง การลงมือแก้ adapter/verifier ตามเอกสารนี้ยังต้องทำเป็น iteration ในพื้นที่แยกและผ่าน review อิสระตามลำดับเดิม
